# Why What or How 创作规范

`Why What or How` 是一组问题驱动的前端技术长文。系列不满足于告诉读者“怎么写”，而是从常见说法、反直觉现象或实际问题出发，依次追问：

- **Why**：为什么会出现这个问题，现有结论哪里不够用？
- **What**：概念究竟是什么，边界在哪里？
- **How**：内部如何工作，怎样通过代码或图解验证？

## 与 What in Browser 的区别

| 系列 | 主要表达方式 |
| --- | --- |
| `What in Browser` | 用拟人角色和故事冲突解释技术机制 |
| `Why What or How` | 作者直接与读者交流，用问题链、代码和图解推导原理 |

本系列不需要强行拟人化。作者口吻、反问、个人判断和适量吐槽都是风格的一部分。

## 文章头信息

每篇文章使用以下头信息：

```yaml
---
title: 文章标题
url: /文章地址
excerpt: 发布时展示的短文案
---
```

- `title` 优先使用明确的问题或概念名称。
- `url` 使用简短、稳定的英文路径。
- `excerpt` 用一个反直觉问题吸引阅读，具体规范见下文。

## 文章结构

### 1. 从问题开始

开头先给出一个值得追问的问题，常见来源包括：

- 大家经常背诵，但无法解释反例的结论。
- 相同代码在不同环境下出现不同结果。
- 一个看似简单的 API 背后存在隐藏条件。
- 两种方案表面相似，实际职责和代价不同。
- 一个基础概念被大量文章直接跳过。

不要先罗列学习目标，也不要一上来展示完整 API 清单。

### 2. 建立概念与背景

- 解释名词的准确含义。
- 必要时补充历史，说明概念为什么会出现。
- 区分语言、规范、宿主环境和具体实现。
- 指出常见说法适用的范围，以及无法解释的情况。

历史只为理解当前机制服务，不写成与主问题无关的年表。

### 3. 逐层推导

推荐使用以下节奏：

1. 给出一个初步结论。
2. 提出反例或新的疑问。
3. 修正模型。
4. 用代码、图解、表格或浏览器结果验证。
5. 继续讨论限制、例外和实际取舍。

疑问应当真的推动下一节内容，而不是只在句尾添加问号。

### 4. 回到实际使用

解释完机制后，再讨论：

- API 或语法应当怎样使用。
- 两种方案各自承担什么职责。
- 常见错误为什么会发生。
- 方案在工程中的成本和边界。
- 作者的使用偏好及其理由。

个人观点需要给出推理过程，不能只写“推荐”或“不推荐”。

### 5. 用问题收尾

多数文章以一组问题代替机械复述。这些问题应能检查读者是否理解文章的核心模型，例如：

- 为什么会这样？
- 两个概念之间是什么关系？
- 换一个场景后，结果是否仍然成立？
- 方案的限制是什么？

末尾附上可靠参考资料。涉及标准时，优先引用规范和官方文档。

## 语言风格

- 直接、口语化，像作者坐在读者旁边一起推理。
- 可以使用“那么”“问题来了”“真的如此吗？”“先别急”等过渡。
- 可以使用 `OK`、`emmm`、`bingo` 等轻松表达，但不要密集堆放。
- 允许使用“你”“我”“大家”，不必遵循拟人故事系列的代词限制。
- 幽默、吐槽和个人经历可以保留，但必须服务当前论证。
- 避免端着讲课，也避免为了活泼牺牲准确性。
- 不用“显而易见”“很简单”跳过真正需要解释的步骤。
- 专有名词、代码、属性和命令使用反引号。

## 代码、图解与表格

### 代码

- 示例应当能够验证当前结论，而不是单纯展示语法。
- 从最小例子开始，再逐步增加条件。
- 代码块标注语言。
- 展示输出时说明运行环境和关键前提。
- 输出顺序题必须解释执行过程，不能只给答案。

### 图解

- 内存关系、执行顺序、布局轴线和状态变化优先使用图解。
- 图中只保留当前推导需要的节点和箭头。
- 正文必须解释图中元素，不能用一张图代替论证。
- 同一篇文章中的颜色、箭头和名词保持一致。

### 表格

适合用于：

- 属性与作用的对应关系。
- 不同方案的优缺点。
- 多个运行环境的行为对比。
- 状态、阶段或输入输出映射。

内容存在先后关系时，优先使用步骤或流程图，不要硬塞进表格。

## 技术准确性

- 明确区分 ECMAScript、JavaScript、浏览器 API 和 Node.js API。
- 明确区分标准要求、常见实现与调试工具显示结果。
- 不把便于记忆的口诀当作完整原理。
- 边缘情况应说明用途和重要程度，不让例外淹没主线。
- 浏览器支持、Node.js 行为和标准状态会变化，发布或修订前必须重新核对。
- 引用资料优先级：正式标准、官方文档、权威技术资料、其他文章。

## Excerpt 写法

Excerpt 是核心问题的“预告”，不是章节目录或文章摘要。

### 基本要求

- 通常使用 2～3 个短句。
- 第一处就抛出反直觉现象、常见误解或具体问题。
- 可以连续追问，但问题必须与正文实际回答的内容一致。
- 最后停在即将开始推导的位置，不提前交代完整结论。
- 保持作者与读者直接交流的语气，可以使用“真的如此吗？”“为什么？”
- 技术名词可以出现，但不要堆成知识点列表。

### 推荐结构

#### 常见结论 + 反例

```text
大家都说 A，所以得到 B。可遇到 C 时，这个结论为什么解释不通？
```

#### 现象 + 连续追问

```text
同一段代码出现了两个结果。差异发生在哪里？执行过程到底经历了什么？
```

#### 简单印象 + 隐藏复杂度

```text
这个 API 看起来只做了一件事。条件稍微变化，为什么结果立刻不同？
```

### 避免写法

- “本文介绍 JavaScript 变量、内存和闭包。”
- “通过本文学习 Flex 的所有属性。”
- “这是一篇关于 HTML5 的详细教程。”
- 直接复制目录或总结中的知识点列表。
- 使用“全面掌握”“彻底搞懂”“一文讲透”等空泛承诺。
- 与正文无关的夸张悬念。
- 在 Excerpt 中直接给出所有问题的答案。

## 参考示例

```yaml
excerpt: “原始类型存在栈里，对象存在堆里”——背了这么多年的结论，真能解释闭包吗？先把口诀放到一边，顺着变量的生命周期重新看看 JavaScript 内存。
```

```yaml
excerpt: 地址栏变了，页面为什么没有刷新？刷新一下，history 路由又为什么突然 404？Hash 和 History 的差别，不只是 URL 里有没有一个 `#`。
```

```yaml
excerpt: 对象从哪里找到自身没有的属性？`prototype`、`__proto__` 和 `constructor` 绕来绕去，究竟是谁指向谁？从一次取值开始，把原型链顺着内存关系拆开。
```

## 封面图片风格

### 文件规格

- 尺寸：`1600 × 900`
- 比例：`16:9`
- 格式：PNG
- 路径：`cover/{编号}-{slug}.png`
- 图片中不放文章标题、说明文字、代码、Logo 或水印。

### 整体视觉

- 使用“**3D 超现实技术场景 × 编辑插画**”风格。
- 把文章最值得追问的技术问题变成一处正在运转、崩塌、转换或重新排列的巨大空间。
- 画面不是技术图解，也不是白底设备产品照，而是一帧带有悬念的“视觉谜题”。
- 使用精致的透明玻璃、磨砂亚克力、钴蓝金属、发光轨道和几何技术物件。
- 环境由暖象牙白过渡到浅蓝，带极淡的技术网格、透明建筑和空间雾气。
- 主体结构以钴蓝、深蓝和青色为主，核心问题或结果使用琥珀橙暖光突出。
- 使用电影式方向光、体积光、玻璃折射和适量粒子，体现运动、变化和空间深度。
- 不使用拟人角色，与 `What in Browser` 的动画故事封面形成清晰区别。

### 技术问题与视觉隐喻

封面只选择文章中的一个核心疑问，并将其转换为可见的空间关系：

- 数据和值：透明方块、容器、圆环或不同材质的几何体。
- 内存与生命周期：层叠框架、广阔空间、独立舱室、断开的原位置。
- 数据流与执行过程：发光轨道、隧道、运动拖尾、逐级变化的结构。
- 类型转换：不同输入经过多段转换后得到相同或意外的结果。
- 布局与空间分配：轨道、弹簧、可伸缩方块、换行弯道和对齐装置。
- 事件循环：多层环形轨道、不同速度的通道和插队路径。
- 原型链：逐层向远处延伸的连接结构和属性查找路径。

隐喻必须与正文机制能够对应。封面负责提出问题，不需要把完整答案画出来。

### 构图要求

- 使用动态斜线、汇聚路径、弯曲轨道或正在崩塌的结构制造运动感。
- 优先采用宽广的低机位或三分之四视角，避免平视的设备展示角度。
- 必须包含前景、中景和背景，让技术装置成为一个可以进入的世界。
- 构图可以不对称，但核心变化或结果必须一眼可见。
- 使用远处的透明建筑、轨道和网格补充尺度，不让主体孤零零地放在空白背景上。
- 每张封面可以使用不同的空间与运动方向；统一的是材质、色彩和技术世界观，不是固定构图。
- 为文章列表裁切预留安全空间，核心物件不要紧贴画面边缘。

### 系列参考

- [JavaScript 变量与内存](./cover/01-wwh-js-memory.png)：栈帧正在崩塌，变量却被独立作用域悬在半空。
- [JavaScript 类型转换](./cover/02-wwh-js-var-exchange.png)：两种输入沿不同路径转换，最终得到相同结果。
- [CSS Flex 布局](./cover/03-wwh-css-flex.png)：内容块在轨道上伸缩，并沿弯道进入下一行。

后续封面应参考以上图片的材质、色彩、光线和空间尺度，但不要直接复刻已有场景。

### 避免事项

- 白色空背景上的居中设备、底座或产品模型。
- 每张图都使用相同视角、相同机器和对称构图。
- 拟人角色、卡通表情或动画故事场面。
- 扁平插画、信息图、流程图、UI 截图或写实摄影。
- 画面中出现标题、代码、数字、公式、箭头、随机字符、品牌 Logo 或水印。
- 与技术问题无关的机械细节、装饰粒子或霓虹灯。
- 画面过暗、对比过低，或背景复杂到看不清核心机制。
- 直接模仿具体动画公司、电影或在世艺术家的风格。

### 图片生成提示词模板

```text

视觉风格：精致的 3D 超现实技术场景与编辑插画；钴蓝金属、
透明青色玻璃、磨砂亚克力和琥珀橙发光物件；暖象牙白到浅蓝的
空间氛围，极淡的技术网格、透明建筑和远景薄雾；电影式方向光、
体积光、玻璃折射、运动拖尾和适量粒子。

构图：宽幅低机位或三分之四视角，使用动态斜线或弯曲路径，
前景、中景、背景完整，空间尺度宏大，构图不对称但焦点明确。
不要做成白底居中设备产品图，不要复刻已有封面的空间结构。

不要人物，不要拟人角色，不要标题，不要文字，不要代码，
不要数字或公式，不要箭头，不要 Logo，不要水印，不要信息图，
不要扁平插画，不要随机字符。
```

## 发布前检查

- [ ] 头信息包含 `title`、`url` 和 `excerpt`。
- [ ] 开头提出了全文真正要回答的问题。
- [ ] 文章沿着 `why → what → how` 推进。
- [ ] 每一个新问题都推动了后续论证。
- [ ] 代码、图解或表格确实验证了结论。
- [ ] 已区分规范、宿主环境和具体实现。
- [ ] 个人观点给出了理由和适用边界。
- [ ] 总结问题能够检查对核心模型的理解。
- [ ] Excerpt 是问题预告，不是内容摘要。
- [ ] 涉及时效性的技术细节已经重新核对。
- [ ] 参考资料完整，并优先使用官方来源。
- [ ] 封面为 `1600 × 900` PNG，并只表现一个核心技术疑问。
- [ ] 封面使用超现实技术场景，而不是白底居中设备图。
- [ ] 封面材质、色彩和光线与现有系列保持一致。
- [ ] 封面没有标题、文字、代码、Logo、水印或随机字符。
