# What in Browser 创作规范

`What in Browser` 是一个用拟人故事解释浏览器与前端原理的系列。文章不从定义和结论讲起，而是把技术概念变成角色、场所、工具和工作制度，让原理随着故事里的问题自然出现。

## 文章头信息

每篇文章使用以下头信息：

```yaml
---
title: 文章标题
url: /文章地址
excerpt: 发布时展示的短文案
---
```

- `title` 要像故事标题，有画面、冲突或一点意外，避免直接写成知识点名称。
- `url` 使用简短、稳定的英文路径。
- `excerpt` 的具体写法见下文。

## 写作风格

### 故事先行

- 从一个正在发生的场景切入，不先铺定义、背景或学习目标。
- 尽快制造问题：拥堵、争吵、误会、罢工、抢生意、警报、工作失误都可以成为开端。
- 技术概念以角色、场所、工具或规章出现，并在解决问题的过程中解释原理。
- 每篇围绕一个核心问题推进，不为了罗列知识点打断故事。
- 章节标题也是情节节点，例如“太慢了！”“拒绝关门”“反复横跳”，不要全部写成教科书式名词。

常用结构：

1. 日常工作突然出问题。
2. 角色围绕问题产生冲突或疑问。
3. 尝试一种解决办法，并展示实际工作过程。
4. 新问题暴露，补充限制、例外或更准确的解释。
5. 用准确的技术描述收住比喻，必要时留下下一篇的线索。

### 语言与节奏

- 整体要活泼、口语化，像角色正在现场工作，不像老师站在讲台上总结。
- 多用短句、动作、语气词和有来有回的对话，避免连续的大段说明。
- 幽默来自角色性格和工作处境，不强行插入与情节无关的段子。
- 可以使用感叹号、问号、省略号和拟声词，但不要每句话都用。
- 对话外尽量不使用“你、我、他”等代词，直接写角色名或省略主语；对话中可按正常口语使用。
- 避免“本文将介绍”“下面带大家了解”“通过本文可以学习”等说明书式表达。

### 世界观与角色

优先复用已有设定，让不同文章发生在同一个浏览器世界中：

- **浏览器老大**：负责协调各部门、制定规则、处理投诉。
- **URL**：携带地址和请求信息，在浏览器与服务器之间奔波。
- **HTTP**：在手术室里拆装请求与响应报文。
- **TCP 老司机**：负责连接、运输和可靠交付，也会带实习生。
- **JavaScript 老大**：在执行大厅工作，常拿着咖啡处理代码和事件。
- **变量大厅**：变量生活和接受内存清理的地方。
- **事件大厅**：任务队列与微任务队列所在的地方。
- **HTML 解析器**：负责搭建页面，经常催促 JavaScript 交工。

新角色应当有明确职责，造型、性格和说话方式要与对应技术概念相符。已有角色再次出现时，不随意改变职责和关系。

### 技术准确性

- 比喻负责降低理解门槛，不能代替技术结论。
- 角色的行为必须能映射到真实机制；无法对应的情节不要只为热闹硬加。
- 关键概念在故事后段用准确语言说明，尤其要写清适用条件、限制和例外。
- 技术名词、字段、代码和按键使用反引号，例如 `TCP`、`Cache-Control`、`Promise`。
- 代码块标注语言，示例保持精简，只服务当前情节。
- 不确定或容易过时的技术细节，应先核对可靠资料再写入正文。

## Excerpt 写法

Excerpt 是文章的“预告片”，目标是让读者产生点开的欲望，不是总结文章讲了哪些知识。

### 基本要求

- 通常写 2～4 个短句，控制在一小段内。
- 直接截取正文中最有画面的冲突、疑问、反差或包袱。
- 可以用一小句对话、连续追问、拟声词或省略号制造节奏。
- 只把问题推到读者面前，不急着给答案，也不要把文章结论提前说完。
- 对话外尽量不出现“你、我、他”；需要代指时，优先写 URL、hash、TCP、浏览器等角色名。
- 保持正文语气，不使用宣传口号或生硬的阅读引导。

### 推荐句式

- **意外开场**：正常工作突然出了岔子，接一句追问。
- **角色冲突**：一个角色被拦下、质疑、催促或抢了工作。
- **连续发问**：围绕文章核心机制抛出两三个具体问题。
- **反差收尾**：前半句看起来一切顺利，最后一句突然翻车。
- **悬念收尾**：在答案出现前停住，用问号或省略号结束。

### 避免写法

- “本文介绍 URL 的组成以及浏览器访问服务器的过程。”
- “通过 TCP 老司机的故事，理解三次握手和四次挥手。”
- “本文将带你深入了解 JavaScript 闭包。”
- 只堆砌技术名词，没有场景、冲突或疑问。
- 先写“我是 URL”“我是 TCP”之类的固定自我介绍，再机械概括全文。
- 结尾补“快来一起看看吧”“跟着文章寻找答案”等通用引导。

### 风格示例

```yaml
excerpt: 凌晨 3 点，一个 URL 被浏览器扔进了网络。睡了一觉醒来，怎么就到服务器了？这一路到底发生了什么？
```

```yaml
excerpt: URL 都出发去服务器了，hash 却被浏览器一把拽了下来：“你不能去！”凭什么？更扎心的是，等了半天，却只被安排去找一个元素……
```

```yaml
excerpt: 函数早已执行结束，临时工作室却死活关不掉。清理员刚碰门把手，警报立刻响起：“该环境仍可访问，禁止清理！”到底哪把钥匙还没交回来？
```

## 封面图片风格

### 文件规格

- 尺寸：`1600 × 900`
- 比例：`16:9`
- 格式：PNG
- 路径：`cover/{编号}-{slug}.png`
- 图片中不放文章标题、说明文字、Logo 或水印。

### 整体视觉

- 精致的 3D 动画电影质感，带轻微黏土或软塑料玩具材质。
- 圆润、可爱但不过分幼儿化，角色表情夸张且清晰。
- 浏览器内部像一座深夜运转的复古未来工厂、控制中心或地下城市。
- 环境以深蓝、藏青和青色为主，关键装置、数据与主动作使用橙黄暖光。
- 使用电影式灯光、体积光、景深和高对比冷暖色，让画面有戏剧感。
- 保留丰富环境细节，但第一眼必须能看懂主角、动作和冲突。

### 角色与隐喻

- 基础角色使用圆润的豆子、胶囊或卵石造型，配大眼睛、眉毛、手脚和明显表情。
- 通过服装和道具区分职责，例如制服、白大褂、领带、工具包、毛线帽或忍者装。
- 同一角色跨封面出现时，尽量保持体型、主色、服装和标志性道具一致。
- 把抽象机制变成能看见的物件：
  - 数据与报文：发光方块、包裹、传送带。
  - 网络传输：隧道、轨道、传送门。
  - 队列与事件循环：环形跑道、排队通道。
  - 内存与变量：座位区、房间、储物格。
  - 作用域与闭包：上锁房间、发光钥匙、连接线。
- 隐喻应直接服务文章核心，不要在一张图里塞入所有知识点。

### 构图要求

- 选择正文里最有冲突的一幕，画成一帧正在发生的故事，而不是角色合照或概念拼贴。
- 主角和关键动作放在视觉中心附近，避免贴边或被背景细节淹没。
- 使用前景、中景、背景建立空间层次；背景可以出现排队角色、机器或通道，补充忙碌感。
- 一张图只保留一个主要动作，例如“被拦下”“正在手术”“冲进变量大厅”“房间拒绝关闭”。
- 表情和肢体动作要能独立讲清情绪：焦急、委屈、得意、疲惫、震惊或愤怒。
- 为文章列表裁切预留安全空间，重要脸部和道具不要靠近四周边缘。

### 避免事项

- 扁平插画、二维图标拼贴、信息图或写实摄影风格。
- 大面积纯白背景、日间自然光或与系列脱节的现实办公室。
- 角色表情相同、整齐站成一排、缺少动作和故事冲突。
- 画面里出现可读文字、随机字符、品牌 Logo、浏览器 Logo 或水印。
- 过度恐怖、阴暗到看不清主体，或机械细节多到喧宾夺主。
- 直接模仿具体动画公司、电影或在世艺术家的风格。

### 图片生成提示词模板

```text
为《{文章标题}》生成系列文章封面，1600×900，16:9，PNG。

场景取自文章中的核心冲突：{用一两句话描述正在发生的动作}。
主角：{角色造型、服装、表情、动作}。
配角与环境：{帮助说明冲突的角色、装置和空间}。

视觉风格：精致的 3D 动画电影质感，圆润的豆子或胶囊形拟人角色，
轻微黏土与软塑料材质；深蓝、藏青、青色的复古未来浏览器工厂，
橙黄暖光照亮关键角色和技术物件；电影式构图，体积光，景深，
丰富但有秩序的机械细节，夸张而清晰的表情。

构图：单一故事瞬间，主动作明确，前中后景完整，主体不贴边，
重要表情和道具清晰可见。

不要标题，不要文字，不要 Logo，不要水印，不要信息图，
不要扁平插画，不要写实人类，不要角色合照，不要随机字符。
```

## 发布前检查

- [ ] 头信息包含 `title`、`url` 和 `excerpt`。
- [ ] 开头迅速进入场景，并在前几段出现问题或冲突。
- [ ] 全文只围绕一个核心问题推进。
- [ ] 对话外没有不必要的“你、我、他”。
- [ ] 比喻与真实技术机制能够对应。
- [ ] 关键结论准确，并写明必要的限制或例外。
- [ ] Excerpt 有画面和悬念，不是内容摘要。
- [ ] 封面为 `1600 × 900` PNG，风格与现有系列一致。
- [ ] 封面没有标题、Logo、水印或随机文字。
